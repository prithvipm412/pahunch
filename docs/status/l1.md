  - Wires and closed switches merge grid points via union-find; open switches are removed.
  - Batteries are stamped as their Norton equivalent (default 3 V, fixed 0.5 Ω internal

## Phase 2 — Sparsh mode (audio + touch circuit builder)

- Added `src/physics/describe.ts`: `describeCircuit(netlist)` returns `{ counts, topology }`

  summary. `topology` is `'empty'` (no components), `'incomplete'` (no battery, or battery not

## Phase 3 — Guided lesson (demo)

- Added an optional guided lesson, started from any mode with a **two-finger double-tap**
  (new `TWO_FINGER_DOUBLE_TAP` event). It resets the netlist/cursor and walks the student through
  building 1 battery + 2 bulbs in **series**, running it, then rebuilding the same two bulbs in
  **parallel** and running again — all still inside `sparshReducer`, so it's covered by the same
  pure-reducer test strategy as the rest of Sparsh.
- Step completion is detected structurally from the netlist via `describeCircuit()` (part counts
  + topology), **not** from exact grid coordinates — a step is "done" when e.g. `counts.bulb >= 2`
  or `topology === 'series'`, so the student can build in any order or any shape on the grid and
  still be recognized. `advanceLesson()` loops so an out-of-order build (e.g. both bulbs placed
  before the battery) cascades through every step it already satisfies in one dispatch — see
  the `'cascades through steps already satisfied out of order'` test in `machine.test.ts`.
- Lesson state is `{ phase: 'series' | 'seriesRun' | 'parallel' | 'parallelRun'; stepIndex }` on
  `SparshState.lesson` (`null` when no lesson is active). `seriesRun`/`parallelRun` mean "build is
  done, waiting for the two-finger tap to run"; the transition out of them happens inside
  `handleSolveResult` so it only fires on a real successful `solve()`, not just on finishing the
  build.

  request**: the existing double-tap placement flow (from Phase 2) could only start a new part
  from an *empty* dot. But closing any loop — including this lesson's own series circuit —

- The lesson's own test (`'walks the full series build -> run -> parallel rebuild -> run demo

## Phase 4 — Tap-count gesture scheme (replaces the double-tap menu)

Replaced Sparsh's menu-based part selection (double-tap → cycle with swipes → double-tap to
confirm) with a tap-count/hold scheme. This removed the `partMenu`/`placingWire`/`editMenu`
`BuildSubMode` variants, the old `DOUBLE_TAP` and `LONG_PRESS` events, and `editMenuOptionsFor()`/
`editMenuOptionClip()` entirely, replacing them with `{ kind: 'idle' } | { kind: 'partChosen';
partType }` and a `pendingTapCount` counter on `SparshState`. All of it is still inside the pure
reducer — `index.tsx` only turns raw touches into `TAP` / `TAP_FINALIZE` / `TAP_RESET` / `HOLD` /
etc. events; it never decides what a tap count *means*.

- **One finger.** Swipe moves the cursor and always announces position-then-part (unchanged
  behavior, reworded clip text). Idle taps accumulate in `pendingTapCount`; `index.tsx` dispatches
  `TAP_FINALIZE` 350ms after the last tap with no new one. The reducer interprets the finalized
  count: 1 = repeat position+part when idle, or *cancel* the chosen part (`'cancelled'`) when one
  is already chosen; 2 = wire, 3 = bulb, 4 = resistor (and anything above 4 clamps to resistor).
  `HOLD` (≥600ms, no movement) chooses battery *unless* `pendingTapCount` is already 1 at the
  moment it fires, in which case it's "tap, then hold" → switch. This is the key design decision
  that keeps hold-disambiguation in the reducer instead of index.tsx: `index.tsx` always dispatches
  the same generic `HOLD` event; the reducer alone decides what it means, by reading the tap count
  it already tracks. Once a part is chosen, the next swipe places it from the cursor to the
  neighbour dot in that direction, speaks `['placed', <part>]`, and **moves the cursor onto the
  new dot** (new — previously the cursor stayed put) so the student can keep building without
  re-navigating. Off-grid or already-occupied-segment placements are refused (`'edge'` /
  `'segment_occupied'`) and keep the part selected. Wire is sticky: it stays chosen after placing
  so consecutive swipes keep laying wire, until a 1-tap cancel or a different part is chosen.
  Every part has its own chosen-vibration pattern (`CHOICE_VIBRATION` in `machine.ts`), felt the
  instant it's chosen, not when it's placed.
- **Timing race fixed while building this**: a naive implementation would finalize the 350ms tap
  count *during* a 600ms hold-in-progress, turning every "tap, then hold" into a plain hold. Fixed
  by having `index.tsx` pause (not reset) the tap-finalize timer for the duration of every new
  one-finger press, only letting it run during the gaps between taps.
- **Two and three fingers.** 2-finger tap still runs `solve()` / toggles Explore mode exactly as
  before. 2-finger *hold* (≥600ms) now gives the spoken summary (`TWO_FINGER_HOLD`, replacing the
  removed 1-finger long-press). 2-finger swipe down removes the most recently placed part
  touching the cursor (`findLatestComponentAt()` — scans the append-ordered array from the end,
  unlike the existing first-match `findComponentAt()`); swipe up toggles a switch there; swipe left
  still goes home; double-tap still (re)starts the guided lesson, now resetting `pendingTapCount`
  too. 3-finger tap speaks a new `'help'` clip listing every gesture.
- **Removing the empty-dot restriction simplified the guided lesson.** Phase 3's "'add' edit-menu
  option" hack (needed because placement used to require an empty starting dot) is gone — Phase 4
  never had that restriction in the first place, since choosing a part no longer depends on
  whether the cursor's dot is occupied. One side effect the lesson's own test caught: placing a
  part now moves the cursor onto it, so chaining placements around the same build (e.g. the
  lesson's series square) needs *no* extra cursor swipes between them any more — but a sticky wire
  placement leaves wire still selected, so a plain cursor-move swipe right after closing a loop
  with wire must cancel (1 tap) first, or it tries to place more wire instead of moving.
- **The parallel-rebuild step's gesture path changed** (the step-*detection* logic —
  `describeCircuit()`'s `counts`/`topology` — did not): Phase 3's test reused the exact same grid
  edge for both parallel bulbs via the old 'add' trick. Since `segmentOccupied()` now firmly
  disallows a second component on a segment that already has one (confirmed by a test, then
  deleted when it turned out to contradict that design), the lesson's own test instead removes the
  old bulb, patches the gap with a wire, and adds the new bulb on a fresh pair of dots connected
  back to the same two electrical nodes by two connector wires — demonstrating that the whole
  rebuild is achievable with ordinary placement gestures and no edge-reuse special case.
- Updated `welcome`/`talkback_hint`/`grid_intro` to describe the new scheme and point to the new
  3-finger help gesture; reworded the guided lesson's step instructions (`lesson_step_battery`,
  `lesson_step_bulb1/2`, `lesson_step_close_loop`, `lesson_parallel_intro`) for the new taps/hold
  vocabulary — the lesson's *mechanics* (which netlist shape completes each step) are unchanged.
- Added `src/sparsh/clips.csv` (`file,en` columns) listing every clip Sparsh uses, for later
  voice-recording — all of `clips.ts`'s keys individually, except the 25 `pos_r{row}c{col}` clips,
  which collapse into one `pos_template` row (`"Row {r}, column {c}."`) since they're all the same
  sentence with two numbers substituted in.
- `machine.test.ts` was substantially rewritten for the new scheme: 38 tests now (up from 27),
  covering tap-count finalization 1–4 (and clamping above 4), `TAP_RESET`, hold vs tap-then-hold
  (including the 2+-taps-then-hold fallback), sticky wire, placement cursor movement, the
  segment-occupied refusal, 2-finger-hold summary, swipe-down remove (most-recent-wins),
  swipe-up toggle, 3-finger help, and the full lesson walkthrough rebuilt for the new gestures
  (still calls the real `solve()` on the exact netlist a student's gestures would produce, at
  both run checkpoints). 84 tests pass across the whole repo; `npm run typecheck && npm test &&
  npm run build` all pass.

## Phase 4b — Undo, safer exit, gesture-clash hardening

### Final gesture map (as requested — this is now the single source of truth; no two gestures
share a meaning)

- **1 finger** — swipe ↑↓←→: move cursor, or place the chosen part. Tap count: 1 = where am I
  (or *cancel* the chosen part, if one is chosen); 2 = wire; 3 = bulb; 4 = resistor. Hold (≥600ms,
  no prior tap) = battery. Tap, then hold = switch.
- **2 fingers** — tap: run / stop (toggle Build↔Explore). Double-tap: guided lesson. Hold: spoken
  summary. Swipe ↓: remove the part at the cursor. Swipe ↑: toggle a switch at the cursor.
  Swipe ←: home (needs a second swipe ← within 3s to confirm). Swipe →: **undo**.
- **3 fingers** — tap: spoken help (lists every gesture above).

### Undo

- `SparshState.history: HistoryEntry[]` (capped at `MAX_HISTORY = 50`, oldest dropped) holds
  `{ netlist, cursor, undoneClips }` snapshots taken **before** every placement, removal, or
  switch toggle — `pushHistory()` in `machine.ts`. Moving the cursor, and choosing/cancelling a
  part, never call it, per the task's rule.
- `undoneClips` is precomputed at push time, not reconstructed on undo: placing a part is undone
  by `[part, 'removed_suffix']` ("Bulb removed."), removing one by `[part, 'is_back']` ("Bulb is
  back."), toggling a switch by `switchClipFor()` of the *pre-toggle* state ("Switch open."/
  "Switch closed."). `TWO_FINGER_SWIPE_RIGHT` → `handleUndo()` pops the stack, restores the
  snapshot, and speaks `['undone', ...undoneClips, pos_r{row}c{col}]` + vibrates `[15,40,15]`.
  Empty history speaks `'nothing_to_undo'`.
- Ordering in `handleUndo()` follows the task's own priority exactly: a chosen-but-unplaced part
  is cancelled first (history untouched); then, in Explore mode, the run is stopped (reusing the
  same `exitExplore()` helper `TWO_FINGER_TAP` now also calls, so the parallel-rebuild lesson
  reminder still fires if due) *and then* the pop happens, in the same dispatch — not a second
  gesture.
- **The lesson re-derives its own step from the restored netlist, not just its recorded
  `stepIndex`** (`recomputeLessonAfterUndo()`): since `stepIndex` only ever moved forward as the
  student built, it can be stale after a rewind. This recomputes within whichever phase family
  (series/parallel) the lesson is already in — a known, documented simplification: undo never
  jumps the lesson backward from 'parallel' to 'series', since it's meant for undoing a recent
  mistake, not rewinding across a whole run checkpoint.
- `TWO_FINGER_DOUBLE_TAP` (restart the lesson) also clears `history` — the old entries point at
  netlists from before the reset, which would be confusing to "undo" back into.

### Safer exit

- `TWO_FINGER_SWIPE_LEFT` now carries `now: number` (so the reducer stays pure — no `Date.now()`
  calls inside it) and checks it against `SparshState.pendingExitAt`. A first swipe sets
  `pendingExitAt` and speaks `'exit_confirm'`; a second one within `EXIT_CONFIRM_WINDOW_MS`
  (3000ms) confirms and leaves. There's deliberately no explicit "reset" path for a lapsed
  `pendingExitAt` — an old timestamp just fails the window check on the next swipe and is
  overwritten, which *is* "resets silently."
- Browser/hardware Back is intercepted in `index.tsx`: `history.pushState()` on mount plus a
  `popstate` listener that immediately pushes another entry (cancelling the back navigation) and
  dispatches `BACK_INTERCEPTED` (→ speaks `'exit_blocked_back'`). Cleaned up on unmount. The
  listener reads `dispatch` through a ref (`dispatchRef`) rather than closing over it directly,
  since the effect only runs once on mount but `dispatch`'s identity can change across renders.

### Gesture-clash hardening

- **Classification waits for the last finger to lift, and uses the maximum finger count seen.**
  `resolveFingerClass()` (new, pure, in `gestures.ts`) takes every `touches.length` sample
  recorded from the first finger down to the last one up and returns the max (capped at 3). In
  `index.tsx`, `commitClass()` calls it on every touchstart/move/end and *upgrades* the gesture's
  committed class the moment a new finger is seen — so a finger that joins a little late still
  promotes a 1-finger gesture to 2 (or 2 to 3) before the gesture ends, rather than the gesture's
  meaning being decided by whatever the count happened to be at one instant. The committed class
  only ever increases within a gesture, and the final tap/hold/double-tap decision at the last
  lift always uses it, not the live `touches.length`. No artificial "settle" delay was added
  before committing to 1 finger — realistic multi-finger taps land within single-digit-to-low-
  double-digit milliseconds of each other, well inside the time it takes to register genuine
  movement, so immediate upgrade-on-join is enough; flagging this as the deliberate tradeoff if a
  real device ever shows otherwise.
- **One movement threshold for everything.** `SWIPE_THRESHOLD` (26), `TWO_FINGER_SWIPE_THRESHOLD`
  (50), and `TAP_MOVE_THRESHOLD` (18) from Phase 4 are gone, replaced by a single
  `MOVEMENT_THRESHOLD = 40` used for every finger count, per the task's rule ("movement > 40px =
  swipe").
- **Edge-start swipes are ignored.** `isEdgeStart()` (new, pure, in `gestures.ts`) checks whether
  a gesture's start X is within `EDGE_ZONE_PX` (24) of either screen edge. `index.tsx` sets
  `edgeIgnored` once per gesture and skips dispatching any swipe-direction event (1- or 2-finger)
  for it — taps and holds starting there still work normally, since they can't trigger Android's
  system back gesture the way an edge *swipe* can.
- `touch-action: none` on `.sparsh-surface` was already in place from Phase 2/3 — reconfirmed,
  not re-added.
- `gestures.test.ts` grew from 8 to 16 tests (new: `resolveFingerClass`, `isEdgeStart`) and
  `machine.test.ts` grew from 38 to 51 tests, covering: undo after place/remove/toggle, several undos in a row,
  nothing-to-undo, undo while a part is chosen, undo in Explore mode, undo during the lesson,
  history capped at 50, the double-swipe-left exit and its 3-second reset, `BACK_INTERCEPTED`,
  and that 2-finger left/right swipes never move the cursor. 106 tests pass across the whole
  repo; `npm run typecheck && npm test && npm run build` all pass. The two genuinely
  index.tsx-only hardening behaviors (late-joining finger, edge-start ignore) are exercised via
  their pure `gestures.ts` helpers rather than full DOM gesture simulation, since the actual
  touch-event wiring in `index.tsx` isn't something vitest drives directly — consistent with how
  every prior phase here has tested gesture logic.

## For L3: Learn-mode goal-check contract

L3's 12-level Learn feature (`src/learn`) needs to check each level's goal against the student's
netlist. Everything below already exists in `src/physics` — `solve()` (`src/physics/index.ts`)
and `describeCircuit()` (`src/physics/describe.ts`) — and is enough to write every goal-check in
the level list without a second simulator or any new physics code. `describeCircuit()` is
structural only (no MNA solve, cheap to call after every edit); `solve()` runs the real solver
(call it after Run). Both take a `Netlist` and are pure/synchronous.

Relevant shapes (`src/contracts/netlist.ts`):
```ts
interface ComponentResult {
  id: string
  voltage: number
  current: number
  power: number
  state: 'off' | 'dim' | 'normal' | 'bright' | 'overload'
}
interface SolveResult { ok: boolean; components: ComponentResult[]; warnings: string[]; errors: string[] }
// describeCircuit() returns:
interface CircuitDescription {
  counts: Record<'battery' | 'bulb' | 'resistor' | 'switch' | 'wire', number>
  topology: 'series' | 'parallel' | 'mixed' | 'incomplete' | 'empty'
}
```
`SolveResult.errors` / `.warnings` are string codes from `src/physics/validate.ts`:
`'empty'`, `'no_battery'`, `'short_circuit'`, `'open_circuit'`, plus `'solver_failed'` (solver
threw) added only by `solve()`, never by `describeCircuit()`. `'incomplete'` topology covers
*both* `'no_battery'` and `'open_circuit'` — if a level needs to tell those apart (e.g. L4's gap
vs. a missing battery), check `solve(netlist).errors` instead of `describeCircuit()`.

**L1/L2 — one battery + one bulb, series by construction.** Any netlist with exactly one load
is reported as `'series'`:
```ts
describeCircuit(netlist).topology === 'series' // true once a battery + 1 load form a loop
```
For L1/L2 specifically ("place a battery" / "place a bulb") just check counts, no topology needed:
```ts
describeCircuit(netlist).counts.battery >= 1
describeCircuit(netlist).counts.bulb >= 1
```

**L3 — first closed series loop, bulb must glow.**
```ts
const result = solve(netlist)
const bulb = result.components.find((c) => netlist.components.find((n) => n.id === c.id)?.type === 'bulb')
const litUp = result.ok && bulb !== undefined && bulb.state !== 'off'
```

**L4 — mind the gap (open circuit).** Before fix:
```ts
solve(netlist).errors.includes('open_circuit') // true while the gap exists
```
After fix (goal met):
```ts
solve(netlist).ok === true
```

**L5 — switch.** The switch's commanded state lives on the component itself
(`CircuitComponent.closed?: boolean`, input to `solve()`); its *effect* shows up in the result:
```ts
const sw = netlist.components.find((c) => c.type === 'switch')
sw?.closed === true   // closed
sw?.closed !== true   // open (undefined or false)
// after solve(), a result for an open switch always has current 0, state 'off':
const swResult = solve(netlist).components.find((c) => c.id === sw?.id)
swResult?.state === 'off' && swResult?.current === 0
```
Run once with `closed: true` and once with `closed !== true` (same netlist, flip the field,
re-run `solve()`) to check "closed then open" per the level flow.

**L6 — series (two bulbs, one loop).**
```ts
describeCircuit(netlist).topology === 'series' && describeCircuit(netlist).counts.bulb === 2
```

**L7 — parallel (two bulbs, two branches).**
```ts
describeCircuit(netlist).topology === 'parallel' && describeCircuit(netlist).counts.bulb === 2
```

**L8 — one bulb out (series, then parallel).** Just compare bulb count against the preloaded
layout's count, in each preloaded netlist:
```ts
describeCircuit(netlist).counts.bulb === preloadedBulbCount - 1
```
No topology check needed — removing one bulb from either preload is the whole goal; `solve()`
after Run will naturally show the open branch / open loop if not yet fixed (series) or the
remaining bulb still lit (parallel branch removed).

**L9 — resistor dims a bulb.**
```ts
const result = solve(netlist)
const bulb = result.components.find((c) => netlist.components.find((n) => n.id === c.id)?.type === 'bulb')
describeCircuit(netlist).counts.resistor >= 1 && result.ok && bulb?.state === 'dim'
```

**L10 — short circuit danger.** Before fix:
```ts
solve(netlist).errors.includes('short_circuit') // true while the dangerous wire is present
```
After the wire is removed (goal met):
```ts
!solve(netlist).errors.includes('short_circuit')
```

**L11 — fault hunt (two faults, e.g. a gap + a short).** Just combine the L4 and L10 checks —
both error codes live in the same `errors` array:
```ts
const errs = solve(netlist).errors
const hasGap = errs.includes('open_circuit')
const hasShort = errs.includes('short_circuit')
// goal met once both are false (solve(netlist).ok === true also works, since any remaining
// error makes ok === false)
```

**L12 — final challenge: one switch, two bulbs in parallel, both bright.**
```ts
const desc = describeCircuit(netlist)
const result = solve(netlist)
const bulbResults = result.components.filter(
  (c) => netlist.components.find((n) => n.id === c.id)?.type === 'bulb',
)
const sw = netlist.components.find((c) => c.type === 'switch')
const goalMet =
  desc.topology === 'parallel' &&
  desc.counts.bulb === 2 &&
  sw?.closed === true &&
  result.ok &&
  bulbResults.every((b) => b.state === 'bright')
```
Note: `'bright'` is a specific brightness band (see `BULB_BRIGHT_RATIO` in
`src/physics/constants.ts`), stricter than `'normal'`. Two bulbs in parallel each draw the full
battery voltage (same as a single bulb alone), so they should land in `'bright'` or `'normal'`
depending on the exact resistor/voltage constants — worth a quick manual check against the
current constants before locking L12's exact `state` target, in case `'normal'` is the more
realistic goal than `'bright'` for this grid's default component values.

None of the above requires new `src/physics` code or a new `solve()`/`describeCircuit()` field —
every level's goal-check is a read of existing `SolveResult`/`CircuitDescription` output plus a
look at the netlist's own components (for counts, ids, and the `closed` field). `solve()`'s
signature and `describeCircuit()`'s return shape are both treated as a stable contract; L1 will
flag here if either ever changes.
