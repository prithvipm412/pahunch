# L1 · Claude Code status

## Done

- Replaced the fake solver with a real Modified Nodal Analysis (MNA) solver in `src/physics`.
  - Wires and closed switches merge grid points via union-find; open switches are removed.
  - Batteries are stamped as their Norton equivalent (default 3 V, fixed 0.5 Ω internal
    resistance) so no extra branch-current unknowns are needed; bulbs/resistors default to 10 Ω.
  - Current through zero-resistance wires/closed switches (not directly observable from node
    voltages) is recovered via a per-island spanning-tree subtree-sum of the surrounding
    resistor/bulb/battery currents; redundant/parallel wire edges report 0 (indeterminate split).
  - Bulb state uses `ratio = power / (3^2 / R_bulb)` with thresholds: off < 5%, dim < 50%,
    normal < 150%, bright < 300%, overload ≥ 300%.
  - `src/physics/validate.ts` detects `empty`, `no_battery`, `short_circuit` (direct wire-merge of
    battery terminals, or post-solve battery current > 2 A), `open_circuit` (battery has no closed
    loop excluding its own edge), and `floating:<id>` warnings for components not connected to a
    battery-containing island.
  - `solve()` never throws — singular-matrix / unexpected-error paths fall back to an `ok:false`
    result with every component reported off.
- Added 10 fixtures under `src/contracts/fixtures/` covering single bulb, series/parallel bulbs,
  open/closed switch, bulb+resistor, short circuit, broken wire, mixed series-parallel, and two
  batteries in series — exercised by `src/physics/solve.test.ts` along with series-vs-parallel
  current comparison and a 200-trial randomized-netlist fuzz test.
- `solve()`'s signature is unchanged.

## Phase 2 — Sparsh mode (audio + touch circuit builder)

- Added `src/physics/describe.ts`: `describeCircuit(netlist)` returns `{ counts, topology }`
  — a purely structural (no `solve()` call) read of a netlist, used for Sparsh's long-press
  summary. `topology` is `'empty'` (no components), `'incomplete'` (no battery, or battery not
  in a closed loop, or a closed loop with no load components — reuses `validate()`'s
  `no_battery`/`open_circuit` errors), `'series'` (loads form a single chain, no duplicate
  node-pair and no node touched by 3+ loads), `'parallel'` (all loads share one node pair), or
  `'mixed'` (anything else, e.g. a series run feeding a parallel pair). Covered by
  `src/physics/describe.test.ts`, reusing the existing `src/contracts/fixtures/*.json` plus a
  few hand-built edge cases.
- Built Sparsh as a pure state machine (`src/sparsh/machine.ts`: `sparshReducer(state, event) ->
  { state, effects }`) plus a thin React screen (`src/sparsh/index.tsx`) that only translates
  touch gestures into machine events and executes the returned effects (speak/vibrate/solve/
  sonify/navigate). 55 vitest tests across `machine.test.ts`, `describe.test.ts`, and
  `gestures.test.ts` (pure swipe-direction and touch→grid-point math in `src/sparsh/gestures.ts`)
  cover every gesture path: cursor movement + edges, the part-placement menu, remove/toggle on
  existing parts, long-press summaries for every topology, all `solve()` outcomes on two-finger
  tap, and Explore mode's drag/pulse/rest/exit flow.
- Design decisions not fully spelled out in the task, so documented here: the edit menu for an
  existing part (opened by double-tapping it) has a single action for non-switch parts (remove)
  and two for a switch (remove, toggle), cycled with left/right swipes like the part-placement
  menu; the "toggle" option previews the *resulting* state using the existing `switch_open`/
  `switch_closed` clips (no new clip names were introduced — see Phase-2 task rule 4). A `mixed`
  topology speaks both `in_series` and `in_parallel` in the long-press summary, since no separate
  "mixed" clip exists. One-finger drag in Explore mode is resolved to the nearest grid dot (same
  model as Build-mode cursor movement), not to a continuous position along a component's line.
- Audio: every `playClip` call goes through `src/sparsh/clips.ts`'s `fallbackFor()`, which is
  always the English text per the task spec (independent of the UI's selected language, which
  still picks the clip-file folder). The screen does **not** use `playSequence` from `src/audio`
  because it doesn't accept a fallback per clip — it awaits `playClip(lang, name, fallbackFor(name))`
  in sequence itself instead.
- `npm run typecheck && npm test && npm run build` all pass (55/55 tests). Manually verified in
  Chrome that the unlock overlay, 5×5 grid, cursor, and caption render correctly with no console
  errors; the available browser automation only simulates mouse events, not real touch gestures,
  so the swipe/double-tap/long-press/two-finger flows were verified via the unit tests above
  rather than live in a browser — flagging this so a real device/touch-emulation pass is still
  worth doing before this ships.

## Phase 3 — Guided lesson (demo)

- Added an optional guided lesson, started from any mode with a **two-finger double-tap**
  (new `TWO_FINGER_DOUBLE_TAP` event). It resets the netlist/cursor and walks the student through
  building 1 battery + 2 bulbs in **series**, running it, then rebuilding the same two bulbs in
  **parallel** and running again — all still inside `sparshReducer`, so it's covered by the same
  pure-reducer test strategy as the rest of Sparsh.
- Step completion is detected structurally from the netlist via `describeCircuit()` (part counts
  + topology), **not** from exact grid coordinates — a step is "done" when e.g. `counts.bulb >= 2`
  or `topology === 'series'`, so the student can build in any order or any shape on the grid and
  still be recognized. `advanceLesson()` loops so an out-of-order build (e.g. both bulbs placed
  before the battery) cascades through every step it already satisfies in one dispatch — see
  the `'cascades through steps already satisfied out of order'` test in `machine.test.ts`.
- Lesson state is `{ phase: 'series' | 'seriesRun' | 'parallel' | 'parallelRun'; stepIndex }` on
  `SparshState.lesson` (`null` when no lesson is active). `seriesRun`/`parallelRun` mean "build is
  done, waiting for the two-finger tap to run"; the transition out of them happens inside
  `handleSolveResult` so it only fires on a real successful `solve()`, not just on finishing the
  build.
- **Found and fixed a real blocker while building the lesson's own test, not a Phase-3 feature
  request**: the existing double-tap placement flow (from Phase 2) could only start a new part
  from an *empty* dot. But closing any loop — including this lesson's own series circuit —
  necessarily means connecting two dots that already have parts on them (the ones on either side
  of the gap), which was simply impossible before this change. Fixed by adding a third edit-menu
  option, `'add'` (`editMenuOptionsFor()` in `src/sparsh/machine.ts`), alongside `'remove'`
  (and `'toggle'` for switches): double-tapping an occupied dot, cycling to "add", and
  double-tapping again opens the same part-chooser double-tapping an *empty* dot does. No new
  clip was needed — it previews with the existing `menu_open` clip. This isn't just needed for
  the lesson: without it, Sparsh could never build any circuit with more than one component
  sharing a junction, i.e. essentially any real circuit. The 55 pre-existing tests still pass
  unchanged since `'add'` is always appended after the existing options.
- The lesson's own test (`'walks the full series build -> run -> parallel rebuild -> run demo
  with real gestures and real solve()'` in `machine.test.ts`) drives the *entire* lesson through
  the same event sequences a real student's swipes/taps would produce (including the new `'add'`
  flow to close each loop) and calls the real `solve()` from `src/physics` on the resulting
  netlist at both checkpoints — it's as close to an end-to-end proof that the demo works as a
  unit test can get. The layout it uses is a unit square (every edge one grid step) so every
  placement, including the loop-closing one, is reachable by a single swipe; a layout with a
  longer "return" wire (like the `two-bulbs-series` fixture's) is not buildable through Sparsh's
  gestures at all, since placement is always "the dot you opened the menu on, to its immediate
  neighbor in the swiped direction."
- New clip names (fallback text in `src/sparsh/clips.ts`, see rule there — no change to the Phase
  2 clips): `lesson_intro`, `lesson_step_battery`, `lesson_step_bulb1`, `lesson_step_bulb2`,
  `lesson_step_close_loop`, `lesson_good`, `lesson_series_ready`, `lesson_series_result`,
  `lesson_parallel_intro`, `lesson_parallel_ready`, `lesson_compare`, `lesson_complete`. The
  existing `talkback_hint` fallback text now also mentions the two-finger-double-tap gesture
  (same clip name, just longer fallback text).
- The screen's two-finger-tap gesture now defers firing `TWO_FINGER_TAP` for the
  double-tap window (350 ms) so a second two-finger tap can be recognized as
  `TWO_FINGER_DOUBLE_TAP` instead of firing the single-tap action first; the pairing check itself
  (`isPairedTap()` in `src/sparsh/gestures.ts`, unit-tested) is shared with the existing
  single-finger double-tap detection. This trades a small, deliberate delay on every plain
  two-finger tap (run / toggle-explore) for correct disambiguation — the same tradeoff any
  double-tap-vs-single-tap UI makes.
- 8 new tests (63 total, up from 55): the `'add'` edit-menu option, starting/resetting the lesson
  from both build and explore mode, out-of-order cascading, and the full build→run→rebuild→run
  walkthrough. `npm run typecheck && npm test && npm run build` all pass.

## Phase 4 — Tap-count gesture scheme (replaces the double-tap menu)

Replaced Sparsh's menu-based part selection (double-tap → cycle with swipes → double-tap to
confirm) with a tap-count/hold scheme. This removed the `partMenu`/`placingWire`/`editMenu`
`BuildSubMode` variants, the old `DOUBLE_TAP` and `LONG_PRESS` events, and `editMenuOptionsFor()`/
`editMenuOptionClip()` entirely, replacing them with `{ kind: 'idle' } | { kind: 'partChosen';
partType }` and a `pendingTapCount` counter on `SparshState`. All of it is still inside the pure
reducer — `index.tsx` only turns raw touches into `TAP` / `TAP_FINALIZE` / `TAP_RESET` / `HOLD` /
etc. events; it never decides what a tap count *means*.

- **One finger.** Swipe moves the cursor and always announces position-then-part (unchanged
  behavior, reworded clip text). Idle taps accumulate in `pendingTapCount`; `index.tsx` dispatches
  `TAP_FINALIZE` 350ms after the last tap with no new one. The reducer interprets the finalized
  count: 1 = repeat position+part when idle, or *cancel* the chosen part (`'cancelled'`) when one
  is already chosen; 2 = wire, 3 = bulb, 4 = resistor (and anything above 4 clamps to resistor).
  `HOLD` (≥600ms, no movement) chooses battery *unless* `pendingTapCount` is already 1 at the
  moment it fires, in which case it's "tap, then hold" → switch. This is the key design decision
  that keeps hold-disambiguation in the reducer instead of index.tsx: `index.tsx` always dispatches
  the same generic `HOLD` event; the reducer alone decides what it means, by reading the tap count
  it already tracks. Once a part is chosen, the next swipe places it from the cursor to the
  neighbour dot in that direction, speaks `['placed', <part>]`, and **moves the cursor onto the
  new dot** (new — previously the cursor stayed put) so the student can keep building without
  re-navigating. Off-grid or already-occupied-segment placements are refused (`'edge'` /
  `'segment_occupied'`) and keep the part selected. Wire is sticky: it stays chosen after placing
  so consecutive swipes keep laying wire, until a 1-tap cancel or a different part is chosen.
  Every part has its own chosen-vibration pattern (`CHOICE_VIBRATION` in `machine.ts`), felt the
  instant it's chosen, not when it's placed.
- **Timing race fixed while building this**: a naive implementation would finalize the 350ms tap
  count *during* a 600ms hold-in-progress, turning every "tap, then hold" into a plain hold. Fixed
  by having `index.tsx` pause (not reset) the tap-finalize timer for the duration of every new
  one-finger press, only letting it run during the gaps between taps.
- **Two and three fingers.** 2-finger tap still runs `solve()` / toggles Explore mode exactly as
  before. 2-finger *hold* (≥600ms) now gives the spoken summary (`TWO_FINGER_HOLD`, replacing the
  removed 1-finger long-press). 2-finger swipe down removes the most recently placed part
  touching the cursor (`findLatestComponentAt()` — scans the append-ordered array from the end,
  unlike the existing first-match `findComponentAt()`); swipe up toggles a switch there; swipe left
  still goes home; double-tap still (re)starts the guided lesson, now resetting `pendingTapCount`
  too. 3-finger tap speaks a new `'help'` clip listing every gesture.
- **Removing the empty-dot restriction simplified the guided lesson.** Phase 3's "'add' edit-menu
  option" hack (needed because placement used to require an empty starting dot) is gone — Phase 4
  never had that restriction in the first place, since choosing a part no longer depends on
  whether the cursor's dot is occupied. One side effect the lesson's own test caught: placing a
  part now moves the cursor onto it, so chaining placements around the same build (e.g. the
  lesson's series square) needs *no* extra cursor swipes between them any more — but a sticky wire
  placement leaves wire still selected, so a plain cursor-move swipe right after closing a loop
  with wire must cancel (1 tap) first, or it tries to place more wire instead of moving.
- **The parallel-rebuild step's gesture path changed** (the step-*detection* logic —
  `describeCircuit()`'s `counts`/`topology` — did not): Phase 3's test reused the exact same grid
  edge for both parallel bulbs via the old 'add' trick. Since `segmentOccupied()` now firmly
  disallows a second component on a segment that already has one (confirmed by a test, then
  deleted when it turned out to contradict that design), the lesson's own test instead removes the
  old bulb, patches the gap with a wire, and adds the new bulb on a fresh pair of dots connected
  back to the same two electrical nodes by two connector wires — demonstrating that the whole
  rebuild is achievable with ordinary placement gestures and no edge-reuse special case.
- Updated `welcome`/`talkback_hint`/`grid_intro` to describe the new scheme and point to the new
  3-finger help gesture; reworded the guided lesson's step instructions (`lesson_step_battery`,
  `lesson_step_bulb1/2`, `lesson_step_close_loop`, `lesson_parallel_intro`) for the new taps/hold
  vocabulary — the lesson's *mechanics* (which netlist shape completes each step) are unchanged.
- Added `src/sparsh/clips.csv` (`file,en` columns) listing every clip Sparsh uses, for later
  voice-recording — all of `clips.ts`'s keys individually, except the 25 `pos_r{row}c{col}` clips,
  which collapse into one `pos_template` row (`"Row {r}, column {c}."`) since they're all the same
  sentence with two numbers substituted in.
- `machine.test.ts` was substantially rewritten for the new scheme: 38 tests now (up from 27),
  covering tap-count finalization 1–4 (and clamping above 4), `TAP_RESET`, hold vs tap-then-hold
  (including the 2+-taps-then-hold fallback), sticky wire, placement cursor movement, the
  segment-occupied refusal, 2-finger-hold summary, swipe-down remove (most-recent-wins),
  swipe-up toggle, 3-finger help, and the full lesson walkthrough rebuilt for the new gestures
  (still calls the real `solve()` on the exact netlist a student's gestures would produce, at
  both run checkpoints). 84 tests pass across the whole repo; `npm run typecheck && npm test &&
  npm run build` all pass.

## Interface changes

- `GridPoint.row`/`GridPoint.col` are documented as 0-based (0 to `gridSize - 1`) via a comment
  in `src/contracts/netlist.ts`. No type changes.
- No new exported types were added to `src/contracts`. The fixture shape used by
  `src/physics/solve.test.ts` is a local test-only type, not part of the shared contract.
- New internal (non-exported-from-contracts) modules under `src/physics`: `constants.ts`,
  `unionFind.ts`, `graph.ts`, `mna.ts`, `wireCurrents.ts`, `validate.ts`, and now `describe.ts`
  (exports `describeCircuit()` and the `Topology`/`CircuitDescription` types). `solve()` from
  `src/physics/index.ts` remains the only supported public entry point for physics; `solve()`'s
  signature is unchanged.
- `src/sparsh` is now a full module: `machine.ts` (reducer + types, pure/testable), `clips.ts`
  (clip name + English fallback vocabulary), `gestures.ts` (pure touch-math helpers),
  `sparsh.css`, and `index.tsx` (the screen). Nothing outside `src/sparsh` imports from it.
- `SparshState` gained a `lesson: LessonState | null` field; `src/sparsh/gestures.ts` gained
  `isPairedTap()`, a pure helper shared by the (now removed single-finger, still-present
  two-finger) double-tap detector in `index.tsx`. Both internal to `src/sparsh`.
- **Phase 4 superseded some Phase 2/3 internals** (all internal to `src/sparsh`, no contract or
  `solve()` change): `BuildSubMode` is now `{ kind: 'idle' } | { kind: 'partChosen'; partType }`
  (the old `partMenu`/`placingWire`/`editMenu` variants and `editMenuOptionsFor()`/
  `editMenuOptionClip()` are gone). `SparshEvent` dropped `DOUBLE_TAP` and `LONG_PRESS`, and
  gained `TAP`, `TAP_FINALIZE`, `TAP_RESET`, `HOLD`, `TWO_FINGER_HOLD`, `TWO_FINGER_SWIPE_DOWN`,
  `TWO_FINGER_SWIPE_UP`, `TWO_FINGER_DOUBLE_TAP`, and `THREE_FINGER_TAP`. `SparshState` gained
  `pendingTapCount: number`.
- `src/sparsh/clips.csv` (new) — every Sparsh clip name + English text in `file,en` columns, for
  generating recorded voices later. Not read by any code; `clips.ts` remains the runtime source.
